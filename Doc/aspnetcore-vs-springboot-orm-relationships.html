JPA vs EF Core

Side-by-side relationship mapping code for the current LTS lines: Spring Boot 3.x (Jakarta Persistence 3.1, Hibernate) against ASP.NET Core 8/9 (EF Core 8/9). Same five relationship shapes, shown in both frameworks' native idiom — annotations on the Java side, a mix of data annotations and Fluent API on the .NET side.

Spring Boot / JPA
ASP.NET Core / EF Core

One-to-One

A profile that belongs to exactly one user. JPA puts the owning side's foreign key on whichever entity has @JoinColumn; EF Core infers the same thing from which class holds the dependent's key, or you can state it explicitly with Fluent API.

Spring Boot — JPAUser.java / Profile.java
@Entity
public class User {
    @Id @GeneratedValue
    private Long id;

    @OneToOne(mappedBy = "user", cascade = CascadeType.ALL)
    private Profile profile;
}

@Entity
public class Profile {
    @Id @GeneratedValue
    private Long id;

    private String bio;

    @OneToOne
    @JoinColumn(name = "user_id") // owning side, FK column
    private User user;
}
ASP.NET Core — EF CoreUser.cs / Profile.cs
public class User
{
    public int Id { get; set; }
    public Profile? Profile { get; set; }
}

public class Profile
{
    public int Id { get; set; }
    public string Bio { get; set; } = "";

    public int UserId { get; set; }   // FK by convention
    public User User { get; set; } = null!;
}

// OnModelCreating (Fluent API, optional if
// naming convention "UserId" is followed)
modelBuilder.Entity<Profile>()
    .HasOne(p => p.User)
    .WithOne(u => u.Profile)
    .HasForeignKey<Profile>(p => p.UserId);
Key difference: JPA needs mappedBy on the inverse side to say "I don't own the FK, look at the other field." EF Core has no mappedBy equivalent — direction is resolved by which entity has the FK property, and Fluent API's HasOne().WithOne() chain is only needed when the convention can't guess it.

Many-to-One / One-to-Many

Many orders belong to one customer. In JPA this is two annotated sides of the same relationship. In EF Core it's just two navigation properties — no attribute is required at all if you follow naming conventions.

Spring Boot — JPACustomer.java / Order.java
@Entity
public class Customer {
    @Id @GeneratedValue
    private Long id;

    @OneToMany(mappedBy = "customer",
               cascade = CascadeType.ALL,
               orphanRemoval = true)
    private List<Order> orders = new ArrayList<>();
}

@Entity
public class Order {
    @Id @GeneratedValue
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "customer_id", nullable = false)
    private Customer customer;
}
ASP.NET Core — EF CoreCustomer.cs / Order.cs
public class Customer
{
    public int Id { get; set; }
    public List<Order> Orders { get; set; } = new();
}

public class Order
{
    public int Id { get; set; }

    public int CustomerId { get; set; }   // FK by convention
    public Customer Customer { get; set; } = null!;
}

// Only needed to customize (delete behavior etc.)
modelBuilder.Entity<Order>()
    .HasOne(o => o.Customer)
    .WithMany(c => c.Orders)
    .HasForeignKey(o => o.CustomerId)
    .OnDelete(DeleteBehavior.Cascade);
Key difference: JPA's @ManyToOne / @OneToMany pair is mandatory annotation on both classes. EF Core's convention-based mapping means a plain collection + FK property on the "many" side is often enough — Fluent API only kicks in when you need to override something (delete behavior, a non-standard FK name, a required relationship).

Many-to-Many

Students enrolled in courses. JPA can map a plain join table directly with @ManyToMany. EF Core 5+ can do the same with a "skip navigation," or you can drop down to an explicit join entity when the join table needs extra columns (like EnrolledOn).

Spring Boot — JPAStudent.java / Course.java
@Entity
public class Student {
    @Id @GeneratedValue
    private Long id;

    @ManyToMany
    @JoinTable(
        name = "student_course",
        joinColumns = @JoinColumn(name = "student_id"),
        inverseJoinColumns = @JoinColumn(name = "course_id")
    )
    private Set<Course> courses = new HashSet<>();
}

@Entity
public class Course {
    @Id @GeneratedValue
    private Long id;

    @ManyToMany(mappedBy = "courses")
    private Set<Student> students = new HashSet<>();
}
ASP.NET Core — EF CoreStudent.cs / Course.cs
public class Student
{
    public int Id { get; set; }
    public List<Course> Courses { get; set; } = new();
}

public class Course
{
    public int Id { get; set; }
    public List<Student> Students { get; set; } = new();
}

// Convention alone creates a hidden join table
// "CourseStudent". To name it explicitly:
modelBuilder.Entity<Student>()
    .HasMany(s => s.Courses)
    .WithMany(c => c.Students)
    .UsingEntity(j => j.ToTable("student_course"));
Key difference: JPA always needs @JoinTable spelled out on the owning side. EF Core can generate the join table silently from two list navigation properties alone — UsingEntity is optional, only needed to rename the table or add payload columns to it.

SQL Joins

This is what both frameworks generate under the hood when you actually fetch related rows. Same customer / order tables as the Many-to-One example above: every customer has zero or more orders, and every order belongs to exactly one customer.

INNER JOINonly rows that match on both sides
SELECT c.name, o.id AS order_id, o.total
FROM customer c
INNER JOIN "order" o ON o.customer_id = c.id;

-- Customers with no orders are excluded.
-- Orders with a dangling customer_id are excluded.
LEFT JOIN (LEFT OUTER JOIN)everything on the left, matched or not
SELECT c.name, o.id AS order_id, o.total
FROM customer c
LEFT JOIN "order" o ON o.customer_id = c.id;

-- Every customer appears at least once,
-- even ones with zero orders (order_id/total = NULL).
RIGHT JOIN (RIGHT OUTER JOIN)everything on the right, matched or not
SELECT c.name, o.id AS order_id, o.total
FROM customer c
RIGHT JOIN "order" o ON o.customer_id = c.id;

-- Every order appears, even ones whose customer_id
-- is NULL or doesn't match any customer (name = NULL).
-- Rare in practice: usually rewritten as a LEFT JOIN
-- with the tables swapped, since it reads more naturally.
FULL OUTER JOINeverything from both sides
SELECT c.name, o.id AS order_id, o.total
FROM customer c
FULL OUTER JOIN "order" o ON o.customer_id = c.id;

-- Unmatched customers AND unmatched orders both show up,
-- with NULLs filling in the missing side.

-- MySQL has no FULL OUTER JOIN keyword — emulate it:
SELECT c.name, o.id AS order_id, o.total
FROM customer c LEFT JOIN "order" o ON o.customer_id = c.id
UNION
SELECT c.name, o.id AS order_id, o.total
FROM customer c RIGHT JOIN "order" o ON o.customer_id = c.id;
How each ORM gets here: in JPA/Hibernate, a plain customer.getOrders() triggers a second lazy-load query, but a JPQL JOIN FETCH o.orders (or a Spring Data @EntityGraph) collapses it into one query — an INNER JOIN by default, or LEFT JOIN FETCH to include customers with no orders. In EF Core, .Include(c => c.Orders) compiles to a LEFT JOIN so parents with no children are still returned. Neither ORM generates a RIGHT JOIN or FULL OUTER JOIN on its own — those you write as raw SQL (@Query / createNativeQuery in Spring, FromSqlRaw in EF Core) when you genuinely need them.

Foreign Key Annotations

Both frameworks let you pin down the exact FK column name, nullability, and which side is authoritative.

PurposeSpring Boot (JPA)ASP.NET Core (EF Core)
Name the FK column@JoinColumn(name = "customer_id")[ForeignKey("CustomerId")] or Fluent HasForeignKey()
Mark the non-owning sidemappedBy = "fieldName"Inferred, or Fluent .WithOne(x => x.Nav)
Require the relationship@JoinColumn(nullable = false)Non-nullable FK property, or .IsRequired()
Composite / custom naming@JoinColumns({...})Fluent .HasForeignKey(e => new { e.A, e.B })
Alternate key (non-PK target)referencedColumnName = "code"Fluent .HasPrincipalKey(x => x.Code)
Join table for M:M@JoinTable(...)Fluent .UsingEntity(...)
Key difference: JPA's FK configuration lives almost entirely in annotations on the entity class itself. EF Core supports a similar attribute, [ForeignKey], but idiomatic EF Core pushes most of this into the OnModelCreating Fluent API instead — keeping entity classes as plain POCOs with no persistence-framework attributes on them at all, which is a deliberate style difference between the two ecosystems, not just a syntax one.

Cascade & Delete Behavior

Spring Boot — JPAcascade types
@OneToMany(mappedBy = "customer",
           cascade = CascadeType.ALL,
           orphanRemoval = true)
private List<Order> orders;

// CascadeType: PERSIST, MERGE, REMOVE,
// REFRESH, DETACH, ALL
// orphanRemoval: delete child when
// unlinked from the parent collection
ASP.NET Core — EF Coredelete behavior
modelBuilder.Entity<Order>()
    .HasOne(o => o.Customer)
    .WithMany(c => c.Orders)
    .OnDelete(DeleteBehavior.Cascade);

// DeleteBehavior: Cascade, Restrict,
// SetNull, NoAction, ClientSetNull
// Required nav + collection = cascade
// by convention already
Key difference: JPA cascade covers the full persistence lifecycle (save, merge, delete, refresh, detach) at the application/ORM level. EF Core's DeleteBehavior is narrower and maps closer to what happens at the database (or SaveChanges time) on delete specifically — save/insert cascading in EF Core is just a side effect of the change tracker, not a separate setting you configure.

Lazy vs Eager Loading

Spring Boot — JPAfetch types
@ManyToOne(fetch = FetchType.LAZY)
private Customer customer;

@OneToMany(fetch = FetchType.EAGER)
private List<Order> orders;

// Defaults: @ManyToOne/@OneToOne = EAGER
//           @OneToMany/@ManyToMany = LAZY
ASP.NET Core — EF Coreloading strategies
// Eager: explicit, per-query
var orders = db.Orders
    .Include(o => o.Customer)
    .ToList();

// Lazy: needs virtual nav +
// Microsoft.EntityFrameworkCore.Proxies
public virtual Customer Customer { get; set; }
options.UseLazyLoadingProxies();

// Default with no Include(): not loaded at all
Key difference: JPA has built-in lazy loading as a first-class default. EF Core is eager-or-explicit by default (a navigation property is simply null until you .Include() it), and true lazy loading is an opt-in add-on package rather than a core feature — a deliberate EF Core design choice to avoid surprise N+1 queries.

Full Entity Example

A Blog with many Posts, each post with many Tags via a join table — every relationship type in one place.

Spring Boot — JPABlog / Post / Tag
@Entity
public class Blog {
    @Id @GeneratedValue private Long id;
    private String name;

    @OneToMany(mappedBy = "blog", cascade = CascadeType.ALL,
               orphanRemoval = true, fetch = FetchType.LAZY)
    private List<Post> posts = new ArrayList<>();
}

@Entity
public class Post {
    @Id @GeneratedValue private Long id;
    private String title;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "blog_id", nullable = false)
    private Blog blog;

    @ManyToMany
    @JoinTable(name = "post_tag",
        joinColumns = @JoinColumn(name = "post_id"),
        inverseJoinColumns = @JoinColumn(name = "tag_id"))
    private Set<Tag> tags = new HashSet<>();
}

@Entity
public class Tag {
    @Id @GeneratedValue private Long id;
    private String label;

    @ManyToMany(mappedBy = "tags")
    private Set<Post> posts = new HashSet<>();
}
ASP.NET Core — EF CoreBlog / Post / Tag
public class Blog
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public List<Post> Posts { get; set; } = new();
}

public class Post
{
    public int Id { get; set; }
    public string Title { get; set; } = "";

    public int BlogId { get; set; }
    public Blog Blog { get; set; } = null!;

    public List<Tag> Tags { get; set; } = new();
}

public class Tag
{
    public int Id { get; set; }
    public string Label { get; set; } = "";
    public List<Post> Posts { get; set; } = new();
}

// OnModelCreating
modelBuilder.Entity<Post>()
    .HasOne(p => p.Blog).WithMany(b => b.Posts)
    .HasForeignKey(p => p.BlogId)
    .OnDelete(DeleteBehavior.Cascade);

modelBuilder.Entity<Post>()
    .HasMany(p => p.Tags).WithMany(t => t.Posts)
    .UsingEntity(j => j.ToTable("post_tag"));
